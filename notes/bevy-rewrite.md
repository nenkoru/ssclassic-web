# Keep the port, grow Rust inward

Feasibility of rewriting the game on Bevy (research, 2026-11-24). The sourced notes behind it are in [research/bevy-rewrite/](research/bevy-rewrite/): Bevy platform state, SE1 architecture mapping, effort and strategies, prior art, licensing.

A Rust/Bevy rewrite of Serious Sam: The First Encounter is technically feasible, but it is the most expensive and least certain way to reach this project's goals, and it delivers none of them by itself. The research estimates a full Bevy rewrite at **20–50 person-months with AI agents and 150–300 without**, against **8–20 person-months with AI** to build 128-player war mode, hordes, seamless bridges and new graphics passes directly in Rust behind the existing host API (all figures are estimates derived from published port rates, not measurements). The work that a rewrite must reproduce is mostly not file formats. It is about **54k lines of `.es` gameplay state machines, a hand-written swept-ellipsoid movement system, a per-light shadow-layer lighting look and a bit-deterministic 20 Hz lockstep simulation**. Bevy 0.20 also regresses the web target: the engine is **single-threaded in the browser**, its default backend is WebGL2 without compute, and it breaks its API about every four months. Licensing adds a hard blocker: Serious Engine 1 is **GPL-2.0-only**, and Bevy's default tree pulls in **Apache-2.0-only crates such as `winit` and `cpal`**, which the FSF treats as incompatible with GPLv2. No Rust or Bevy rewrite of any classic 3D shooter, Quake included, has reached verified parity; the ports that succeeded kept the original structure and checked themselves against the original binary. The recommended path is to build a parity oracle, add the war-mode systems in Rust now, translate only the subsystems the new features force you to replace (netcode, collision, ray casts), and revisit Bevy when its web threading, Emscripten interop and licensing questions are settled.

## A rewrite must reproduce 220k lines of behaviour, and the formats are the easy 10%

Measured in this repository, Serious Engine 1.10 has about **238k lines** under `Engine/`, of which about **168k** are code that TFE content actually uses. Skipping Ska skeletal models, Terrain, the Vulkan/Direct3D drivers, the master-server lister and the vendored zlib removes about 70k lines without losing any TFE content ([Engine sources](../src/SamTFE/Sources/Engine/); counts by `wc -l` in the research notes). On top of that sit **120 TFE entity classes in 54,411 lines of `.es`**, plus 7,111 lines of hand-written `Entities/Common` (particles, HUD, path finding) and 3,631 lines of engine base classes written in `.es`, about 65k lines of gameplay in total ([CMakeLists.txt](../src/SamTFE/Sources/CMakeLists.txt)). The engine is Croteam's 2016 GPL release, "the very same engine" used for the original games ([Croteam](https://www.croteam.com/serious-sam-source-code-released/)).

The asset side is tractable. A `.wld` file is a chunked binary dump of the in-memory world. It already contains the sector geometry in double precision, the triangulation, a per-sector BSP tree and per-polygon shadow maps, so a reader only has to parse, not recompute ([WorldIO.cpp](../src/SamTFE/Sources/Engine/World/WorldIO.cpp), [BrushIO.cpp](../src/SamTFE/Sources/Engine/Brushes/BrushIO.cpp)). The catch is that **no public format documentation or non-C++ parser exists**. Searches turned up only other games' `.wld` formats and the community modding Q&A, which documents no internals ([rentry SamClassicQNA](https://rentry.org/SamClassicQNA)). Some structures are raw MSVC 32-bit struct dumps, and several legacy chunk versions are still live. The `.mdl` format is vertex-animated with eight version branches. The only third-party tool found is a C# `.tex` converter that handles neither animated nor procedural textures ([SS1TexConverter](https://www.github.com/purifetchi/SS1TexConverter)). The notes rate the loaders easy to medium and estimate 1.5–2.5k lines of Rust for brushes and world state.

The hard parts sit elsewhere, and each one carries a fidelity risk.

**Entity logic is code, not data.** Monster stats, weapons, damage, AI, effects and particles are compiled into `.es` classes. Each `.es` class mixes raw C++ with a coroutine-style DSL (`wait`, `autowait`, `call`, `jump`, `on (EEvent)`), which Croteam's Ecc compiler lowers into numbered handler functions and an explicit state stack. State IDs are encoded as `classID<<16 | n`, for example `0x012f000e` for Headman ([Headman.cpp](../src/SamTFE/Sources/Entities/Headman.cpp)). The `.wld` files store each entity's properties keyed by these numeric IDs, *and its AI state stack*, so even a level at start is effectively an editor savegame. A rewrite must reproduce every class's property and state numbering or translate entities at import time. The counts give the scale: 465 event handlers, about 889 procedures, 506 random-number calls and about 435 distinct engine API names called from gameplay code. Ecc's grammar is only about 1.6k lines, so a transpiler can emit the DSL skeleton mechanically, but the notes estimate that covers just 25–35% of the text. The rest is pointer-heavy C++ that has to be ported by hand or by LLM.

**Movement feel is hand-written, not physics.** `MovableEntity.es` (3,119 lines) implements swept clipping against brush polygons, stair stepping, sliding and gravity taken from the polygon below, on a fixed 20 Hz tick ([MovableEntity.es](../src/SamTFE/Sources/Engine/Classes/MovableEntity.es), [Timer.cpp](../src/SamTFE/Sources/Engine/Base/Timer.cpp)). Croteam compiles the collision, ray-cast and CSG code with `-fno-unsafe-math-optimizations` to protect determinism ([CMakeLists.txt](../src/SamTFE/Sources/CMakeLists.txt)). Avian or Rapier would change how Sam moves, how monsters step and when projectiles hit, so this code must be ported line for line, not replaced.

**The look depends on runtime shadow-layer mixing.** Each polygon's shadow map is a list of one-bit layers, one per light, which the layer mixer composites every frame with the current, possibly animated, light colour ([LayerMixer.cpp](../src/SamTFE/Sources/Engine/Light/LayerMixer.cpp)). Bevy's `Lightmap` component expects a baked indirect-light image on a second UV channel ([docs.rs](https://docs.rs/bevy/latest/bevy/pbr/struct.Lightmap.html)). That covers static lighting but not flickering lights, so a faithful port needs a custom multi-layer material. The same holds for the three texture layers per polygon, texture-based fog and haze, mirrors and the 3.5k lines of procedural texture effects.

**Networking is deterministic lockstep.** Every tick the server packs all players' actions into one `MSG_SEQ_ALLACTIONS` block, and every client runs the whole simulation ([Server.cpp](../src/SamTFE/Sources/Engine/Network/Server.cpp)). Demos are the same action stream on disk. A rewrite either matches this bit for bit across wasm, x86 and ARM, down to libm's `sin` and `cos`, or it gives up compatibility with original demos and saves.

| Subsystem | SE1 size (lines) | Bevy counterpart | Difficulty | Main risk |
|---|---|---|---|---|
| `.gro` VFS, `.tex`, sound loading | ~2.6k + 1.9k + 6.3k | custom `AssetReader`/loaders, bevy_audio or kira | Easy–medium | path casing, 3D attenuation semantics |
| `.mdl` models and animation | 13.4k + 1.2k | vertex-animation material or morph targets | Medium | model shading from the floor's shadow map |
| `.wld` geometry, BSP, shadows | 7.1k + 7.2k | loader to meshes and collision data | Medium | undocumented raw structs, legacy versions |
| Lighting, world renderer, effects | 4.5k + 7.5k + 3.5k | custom materials and render passes | Medium–hard | "doesn't look like Serious Sam" |
| Movement, collision, ray casts | 3.1k + ~2.6k | hand-ported systems (not Rapier/Avian) | Hard | feel, determinism |
| Entity state machines | 54.4k `.es` + 7.1k + 3.6k | per-class systems plus a state-stack runtime | Very hard (volume) | drift across ~890 procedures |
| Networking, demos, saves | 17.3k | custom lockstep, or lightyear/replicon | Hard (exact) / medium (new) | desync; loss of demo and save compatibility |
| Menus, Netricsa, HUD, console | ~30k | bevy_ui/egui, small interpreter | Medium | volume |

The table summarises the per-subsystem ratings in the architecture notes. Sizes come from local `wc -l`.

## Bevy 0.20 would take the browser build backwards

Bevy reached **0.20 on 8 Oct 2026**, with no 1.0 date and no LTS policy ([Bevy 0.20](https://bevy.org/news/bevy-0-20/)). Releases came in January, June and October 2026. The 0.18→0.19 migration guide alone has **about 103 top-level breaking items**, among them resources becoming components, the scene crate renamed and morph targets restructured ([migration guide](https://bevy.org/learn/migration-guides/0-18-to-0-19/)). Then 0.20 replaced the shader dialect with WESL ([Bevy 0.20](https://bevy.org/news/bevy-0-20/)). The churn concentrates in rendering internals, which is exactly where a custom 2001-style renderer would live. The research budgets about 0.25–0.5 person-months per upgrade, three to four times a year. Ecosystem crates trail the engine: bevy_replicon shipped four releases within the single 0.19 cycle ([replicon README](https://raw.githubusercontent.com/simgine/bevy_replicon/master/README.md)), bevy_matchbox is still on 0.18 ([docs.rs](https://docs.rs/crate/bevy_matchbox/0.14.0/source/README.md)), and the Quake-map plugin bevy_trenchbroom calls itself "on low maintenance/life support" ([lib.rs](https://lib.rs/crates/bevy_trenchbroom)).

The web is where the comparison hurts most. Bevy's own CLI documentation states that **"The Bevy engine does not yet take advantage of multi-threading on the web"**. The experimental opt-in needs nightly Rust and cross-origin isolation, warns of "more bugs and a worse user interface", and only speeds up certain third-party crates ([Bevy CLI](https://thebevyflock.github.io/bevy_cli/cli/web/multi-threading.html)). The root cause is that wgpu's web types are not `Send`/`Sync` ([PR #12205](https://www.github.com/bevyengine/bevy/pull/12205)). The current port, by contrast, already runs the engine in a worker with pthreads and streams GL commands to the page ([roadmap](roadmap.md)). Moving to Bevy would put the ECS, physics, AI and render preparation back on one thread, at the very moment the project wants 10× more monsters.

Rendering reach is no better. WebGL2 is still Bevy's default web backend, and WebGPU is an opt-in feature ([Bevy WebGPU](https://bevy.org/news/bevy-webgpu/)). On WebGL2 there are no compute shaders and no storage buffers. Bevy's occlusion-culling example fails on the storage-buffer limit ([commit, via a mirror](https://tgfed.nhyvvfeijnh.workers.dev/slyedoc/bevy/commit/09ff7ce9f6312e33d75ebdca8c0c68f043751023)), and bevy_hanabi GPU particles require WebGPU ([hanabi](https://raw.githubusercontent.com/djeedai/bevy_hanabi/main/README.md)). WebGPU itself now ships in Chrome, Safari 26 and Firefox on Windows and macOS. Stable Firefox on Linux and Android still lacks it, and on Linux, Chrome enables it only for Intel Gen12+ and NVIDIA on Wayland ([gpuweb status](https://github.com/gpuweb/gpuweb/wiki/Implementation-Status)). A Bevy build therefore still needs a reduced WebGL2 path: CPU frustum culling only, on one thread, and no portal or PVS visibility, which neither Bevy core nor a mature crate provides. The existing port already has both a WebGL2 and a WebGPU backend behind `gl1shim` ([gl1shim.c](../port/common/gl1shim.c)).

Some gaps remain open. No 0.19 or 0.20 wasm size or startup figures were found; the only data point is a 2023 WebGPU example at about 13 MB raw and 3.9 MB compressed ([r/rust, via a proxy](https://axebps-redlib.hf.space/r/rust/comments/13lb0h8/bevy_webgpu/jkr35ga/?context=3)), against roughly 6 MB for today's engine wasm. Bevy's audio stack has known OGG/Vorbis buffering, looping and spatial issues as of 0.19 ([migration guide](https://bevy.org/learn/migration-guides/0-18-to-0-19/)), which matters for a game that ships 55 OGG files alongside 331 WAVs. There is **no shipped Bevy editor**; the `.bsn` scene asset format is still on the "next" list ([Bevy 0.20](https://bevy.org/news/bevy-0-20/)). Commercial Bevy releases number "on two hands" ([youngju.dev](https://www.youngju.dev/blog/culture/2026-05-14-bevy-game-engine-rust-hands-on-ecs-paradigm-modern-gamedev-deep-dive-2026.en)), and the flagship, Tiny Glade, uses Bevy's ECS with its own renderer ([HN summary](https://hn.nuxt.dev/item/41214369)). No fast 3D FPS has shipped on Bevy, on the web or anywhere else.

Bevy's native strengths are real. Version 0.19 rendered a 55,000-entity city in 11.8–16.2 ms and 1.6M culled cubes in 18.8 ms ([Bevy 0.19](https://bevy.org/news/bevy-0-19/)). lightyear offers server-authoritative replication with prediction, rollback and WebTransport on wasm ([lightyear](https://raw.githubusercontent.com/cBournhonesque/lightyear/main/README.md)), and Avian has an `enhanced-determinism` feature ([avian3d](https://docs.rs/avian3d)). Those advantages show up mostly on desktop and WebGPU, not on the browsers and phones this project targets.

## None of the four goals comes from switching engines

Each goal needs new systems that the current SE1 does not have. Switching to Bevy provides frameworks for them but not the systems themselves.

**128-player war mode needs new netcode either way.** SE1 caps players at 16 ([Network.h](../src/SamTFE/Sources/Engine/Network/Network.h)), and lockstep scales badly for reasons unrelated to the engine. Bandwidth is not the problem: 128 players × about 30 bytes × 20 ticks is about 77 KB/s downstream (estimate; action size not measured). The problems are that every phone simulates the entire battle, that one slow or lost input stalls everyone, that late joiners need a full state transfer, and that interest management is impossible when every client needs every input ([Gaffer on Games](https://gafferongames.com/post/deterministic_lockstep/)). The project's roadmap already names interest management as the requirement ([roadmap](roadmap.md)). Reaching 128 means server-authoritative snapshot or delta replication with relevance filtering, prediction for the local player and interpolation for everyone else. That replaces the 17k-line `Engine/Network` and the entity sync model whichever host is used. lightyear publishes no 64–128-client benchmarks, wasm clients included ([lightyear](https://docs.rs/crate/lightyear/0.26.4/source/README.md)), so Bevy offers a starting framework, not a proven solution.

**Hordes are bound by algorithms, not ECS iteration.** On an M-series Mac this engine holds 60 fps at 200 monsters and falls to 36 fps at 500. At 500 monsters, line-of-sight ray casts take about 21% of frame time, collision 14%, path finding 7% and model drawing 9%, and phones are estimated 4–5× slower ([big-ideas §2](big-ideas.md)). Bevy's iteration speed of 10,000 entities in 1.87 µs ([Bevy 0.19](https://bevy.org/news/bevy-0-19/)) addresses a cost that is not the bottleneck. The fixes are flow fields, spatial hashing, simpler attack rules and instanced vertex-animation rendering. All of that is new code in any engine, and the plan in `big-ideas.md` already describes it.

**The two goals pull against each other.** The horde plan assumes a deterministic crowd so that only inputs are sent ([big-ideas §3](big-ideas.md)), while 128 players need interest-managed replication, which lockstep forbids. The project must choose between a hybrid (a deterministic crowd replayed from seeds and inputs, plus replicated "hero" entities) and compressed per-region crowd replication. This design decision dominates the effort in every strategy, and no engine makes it for you.

**Seamless levels and better graphics extend what already works.** Seamless "bridges" need a world tool and per-zone singletons, estimated at 2–4 person-months with AI. Graphics work such as bloom, tone mapping, SSAO, TAA, re-baked lightmaps, KTX2 HD textures and instanced horde drawing can be added as passes in the existing JS/WGSL backends for 1–4 person-months with AI (all estimates from the strategy notes). Moving the renderer into Rust wgpu inside the Emscripten build would actually *lose* WebGPU, because wgpu under Emscripten supports only the GLES path ([wgpu docs](https://wgpu.rs/doc/wgpu/documentation/platforms/emscripten/index.html)).

The net effect is that a Bevy rewrite postpones every goal by the length of the rewrite, then asks for the same new systems afterwards.

## Ports with an oracle finish; redesigns without one stall

The track record is lopsided. No Rust engine rewrite of a classic 3D shooter has reached verified parity. Richter, a Quake engine in Rust, remains "pre-alpha" with its server "still in its early stages" ([richter](https://github.com/cormac-obrien/richter)). Its Bevy successor Seismon "boots and can be played normally", but its author has never finished a full playthrough ([seismon](https://github.com/eira-fransham/seismon)). And Quake is far smaller than SE1. Clean-room reimplementations elsewhere take years: OpenMW started in 2008 and reached version **0.51 in June 2026, with no 1.0 after 18 years** ([Wikipedia](https://en.wikipedia.org/wiki/OpenMW)). Source-based ports reach playability in months. reVC was finished within about seven months of starting ([PC Gamer](https://pcgamer.com/reverse-engineered-gta-iii-source-code-is-back-online)), and DevilutionX went from released source to 1.0 in about 1.5 years ([GamingOnLinux](https://gamingonlinux.com/2020/01/devilutionx-an-open-source-game-engine-for-the-original-diablo-sees-a-big-release)). Ten years of SE1 community work have produced many C++ forks, including Vulkan, Flatpak and Switch builds, and **no re-architecture on Bevy, Godot, Unity or Unreal** ([SeriousSamClassic-VK](https://github.com/tx00100xt/SeriousSamClassic-VK)). A Bevy ECS redesign of SE1 belongs to the slow, clean-room-style group even with the source in hand, because the CEntity class hierarchy and `.es` coroutines do not map onto ECS systems one to one.

AI-assisted porting has changed the economics, but only for structure-preserving translation checked against an oracle. Ladybird moved about **25k lines of LibJS to Rust in about two weeks**, demanding byte-identical ASTs and bytecode and zero test262 regressions ([Ladybird](https://ladybird.org/posts/adopting-rust/)). vjeux ported **about 100k lines of TypeScript to Rust in about four weeks**, then spent about three weeks closing roughly 80 divergences found by 2.4M seeded differential battles ([vjeux](https://blog.vjeux.com/2026/analysis/porting-100k-lines-from-typescript-to-rust-using-claude-code-in-a-month.html)). His failure modes are a warning: the agent "simplified" logic, duplicated structs, and **edited the reference source it was supposed to treat as the oracle**. The fish shell's hand-made port of about 57k lines of C++ took about 14 months, with about seven core contributors ([fish](https://fishshell.com/blog/rustport/)). At repository scale, LLM translation accuracy drops to **43.5% computational accuracy**, against about 90% at module level ([DepTrans](https://arxiv.org/html/2604.02852v1), [EvoC2Rust](https://arxiv.org/html/2508.04295v2)). Small, oracle-checked slices therefore beat one-shot translation. A Bevy redesign throws away the per-tick state comparison that makes these rates possible, and verification falls back to playtesting "feel".

From these rates (estimates: 10–25k translated lines per person-month with AI including parity work, 1–2.5k without), the strategy notes derive the following ranges for one developer:

| Strategy | With AI agents | Without AI | Reaches war-mode goals? | Dominant risk |
|---|---|---|---|---|
| (a) Full Bevy rewrite, new ECS architecture and netcode | 20–50 PM | 150–300 PM | Only after the rewrite, plus the same new systems | No oracle, feel drift, Bevy churn, licence conflict, 1–3 year freeze of the shipping port |
| (e) Structure-preserving LLM translation of SE1 to Rust, no Bevy | 12–30 PM | 90–240 PM | No; same game, new language | Divergence tail, libm/float-order desyncs, second idiomatic pass (+30–60%) |
| (c) Bevy renderer beside the SE1 sim (two wasm modules) | 6–14 PM | 18–36 PM | Graphics only | Rebuilding SE1's look in Bevy; WebGL2 limits |
| (c′) Bevy and SE1 in one wasm | 0.5–1 PM spike | — | — | Bevy supports only `wasm32-unknown-unknown`; Emscripten/wasm-bindgen interop is a Sept 2026 experimental preview ([Cloudflare](https://blog.cloudflare.com/rust-workers-emscripten-target/)) |
| (d) c2rust then refactor | Not applicable | — | — | c2rust handles C99, not C++ ([c2rust](https://github.com/immunant/c2rust)) |
| (b)+(f) Strangler fig: new Rust systems behind the host API, renderer passes in place | **8–20 PM** | 25–60 PM | **Yes, directly** | FFI seam cost; the lockstep-vs-replication design choice |

PM = person-months, about 21 working days each. All figures are estimates; no published effort data exists for a comparable game-engine rewrite. The (b)+(f) range breaks down as replication with interest management (3–7 PM), crowd simulation with instanced rendering (2–5), seamless bridges (2–4), graphics passes (1–3) and the parity oracle (1). For a solo developer, option (a) means roughly two to four calendar years before war-mode work can even begin on the new base.

The risk profile differs as much as the cost. A Bevy rewrite carries the long tail that kept OpenMW in beta for a decade. It also carries LogLog Games' complaint, after three years of full-time Rust gamedev, that the compiler forces refactors for small design tweaks ([devtalk](https://forum.devtalk.com/t/lessons-learned-after-3-years-of-fulltime-rust-game-development-and-why-were-leaving-rust-behind/153139)), plus the classic rewrite trap of freezing a working product while discarding years of embedded fixes ([Joel Spolsky](https://www.joelonsoftware.com/2000/04/06/things-you-should-never-do-part-i/)). The strangler fig carries smaller, known risks. Each FFI seam costs glue and some performance, as fish found with autocxx ([fish](https://fishshell.com/blog/rustport/)). The project's append-only host API, now at v10, already runs this pattern ([features](features.md)).

## GPL-2.0-only collides with Bevy's Apache-only dependencies

SE1's headers grant **"version 2 of the GNU General Public License"** with no "or later" clause ([Engine.cpp](https://raw.githubusercontent.com/Croteam-official/Serious-Engine/master/Sources/Engine/Engine.cpp)). Under the FSF's reading, translating code into another language is a modification ([GPL FAQ](https://www.gnu.org/licenses/gpl-faq.html#TranslateCode)), and using an LLM changes nothing. The 2026 chardet dispute, in which an LGPL library was rewritten with Claude and relicensed as MIT, drew objections from the original author, Armin Ronacher and LWN's editor even for a claimed clean-room rewrite ([LWN](https://lwn.net/Articles/1061534/), [Ronacher](https://lucumr.pocoo.org/2026/3/5/theseus/)). A Rust rewrite that follows SE1 code is therefore GPL-2.0-only, and its sources must be offered alongside every wasm build served. A documented clean room, with separate spec writers and implementers and no SE1 source in any LLM context, is not realistic for a team that has already read the engine in depth.

That is a problem because the FSF and Apache both hold that **Apache-2.0 is incompatible with GPLv2**, though compatible with GPLv3 ([FSF](https://www.gnu.org/licenses/license-list.en.html), [ASF](https://www.apache.org/licenses/GPL-compatibility.html)). Bevy itself is MIT OR Apache-2.0, so it can be taken under MIT. A `cargo metadata` scan of a default **bevy 0.20.1** dependency tree, however, found 570 packages including **14 Apache-2.0-only crates**: among them `winit` (windowing), `cpal` (audio), `ab_glyph` (text), `ktx2` and `spirv` (local scan in the licensing notes). Bevy's own `deny.toml` explicitly allows plain Apache-2.0 ([deny.toml](https://raw.githubusercontent.com/bevyengine/bevy/main/deny.toml)), so nothing upstream keeps the tree GPLv2-clean. The existing `rust/` workspace has no Apache-only crates ([Cargo.toml](../rust/Cargo.toml)); the problem starts only when Bevy comes in. The ways out are all costly:

- Strip Bevy's windowing, audio and text and write your own backends, enforced by `cargo deny`.
- Get Croteam/Devolver, and every fork contributor whose code is translated, to relicense as GPL-2.0-or-later.
- Accept a compliance gap, which would also bar the project from strict distributions such as Debian and Fedora.

The scan covered all targets, so the exact set that reaches the wasm build still needs a per-target check.

Game data constrains any engine choice equally. The Steam copy's Devolver EULA forbids "making a copy of this Software available on a network" ([local EULA](../data/tfe-full/license.txt), [Devolver EULA](https://www.devolverdigital.com/eula)), and no redistribution grant was found for the 2001 demo. Browser projects that were taken down served copyrighted assets ([TorrentFreak](https://torrentfreak.com/nintendo-lawyers-file-copyright-complaints-against-super-mario-64-pc-port-200508/)). A Bevy pipeline that converts TFE models and levels to glTF ahead of time would create exactly the kind of derivative asset copies that must never be hosted; conversion has to happen in the user's browser from their own `.gro` files. "Serious Sam" is a Croteam/Devolver trademark ([Justia](https://trademarks.justia.com/owners/devolver-digital-inc-5285337)), so the project name should stay neutral whichever engine it uses.

## Conclusion

The question is less "can SE1 be rewritten on Bevy" than "what does the rewrite buy that the goals need", and the answer today is very little. The real asset this research points to is the **parity oracle**: per-tick world-state hashing during demo and bot-session playback, on top of the bit-identical frame captures the project already has. It costs about 1–2 person-months, and every Rust migration path depends on it. Once it exists, subsystems can move to Rust when a feature forces their replacement, and the obvious first candidates are the 17k-line netcode (which war mode replaces anyway) and the collision and ray-cast hot paths (which hordes must optimise anyway). Each becomes a verified, structure-preserving translation in the style of Ladybird and fish, not a gamble on feel. A cheap side spike worth running is retargeting Croteam's Ecc compiler to emit Rust state-machine skeletons (about 0.5 PM). It would show how much of the 54k-line `.es` corpus can be lowered mechanically, the number that most sets the cost of any eventual full migration.

Bevy becomes worth revisiting when three things change together: Bevy runs its own scheduler multi-threaded on the web, Emscripten–wasm-bindgen interop leaves preview so the C++ simulation and a Rust renderer can share one module, and the GPL-2.0-only versus Apache-2.0 conflict is resolved by relicensing or a GPLv2-clean dependency set. Until then, the project gets to its goals sooner by growing Rust inward from the host API than by asking Bevy to replace an engine that already runs, threaded, in the browser.
